1这个项目在做什么

一句话概括：一个给「新闻资讯类 App」提供数据的后端服务。它对外提供 HTTP 接口，负责用户注册登录、新闻分类与列表、新闻详情与相关推荐、收藏、浏览历史这几块业务；对内把数据存在 MySQL 里，把热点数据缓存到 Redis 里。

它的代码非常典型地体现了「分层架构」这一套工程习惯。你把它吃透，以后看任何一个 FastAPI 项目都能快速定位代码位置。

技术栈与各组件分工

组件在这个项目里干什么
FastAPIWeb 框架。负责接收 HTTP 请求、做参数校验、生成接口文档（访问 /docs）、注入依赖。
UvicornASGI 服务器，真正把服务跑起来的进程。uvicorn main:app --reload 就是启动它。
SQLAlchemy 2.0ORM 框架。用 Python 类来描述数据库表，用 Python 对象来增删改查，避免手写 SQL 字符串。
aiomysqlMySQL 的异步驱动。SQLAlchemy 通过它把异步的 ORM 操作翻译成 MySQL 能听懂的协议。
Pydantic v2数据契约。校验前端传来的 JSON 是否合法，同时规定返回给前端的数据长什么样。
redis.asyncio异步 Redis 客户端，做旁路缓存，减少数据库压力。
passlib + bcrypt密码哈希。绝不存明文密码，只存不可逆的 bcrypt 哈希串。

2分层架构与职责边界

这个项目最核心的一条设计原则是：每一层只做一件事，且只和相邻层打交道。请求像水流一样自上而下穿过各层，绝不允许「跨层抄近道」（比如在路由函数里直接写 SQL）。

各层职责与「红线」

层该做的事绝对不该做的事（红线）
routers/ 定义 URL、声明依赖（Depends）、调 crud、按统一格式返回 不写 SQL，不做密码加密，不直接操作 db.execute()
crud/ 拼 SQL、执行增删改查、返回数据（ORM 对象或 dict） 不接 HTTP 请求，不拼 {code, message, data} 响应格式，不知道 URL 是什么
models/ 用类描述表结构：字段、类型、索引、外键、默认值 不写业务逻辑，不做查询
schemas/ 定义接口收发的数据结构，做字段校验与类型转换 不碰数据库，不含 ORM 映射
cache/ 设计缓存 key、决定过期时间、调用底层 Redis 读写 不直接连 Redis（那是 config/cache_conf.py 的活）
config/ 创建引擎、会话工厂、Redis 客户端这类全局基础设施 不含任何业务判断
utils/ 跨层复用的纯工具：加密、认证依赖、响应封装、异常处理 不引入 routers 等上层模块（避免循环依赖）
为什么要这样分层？

假设某天新闻列表的查询要加一个「只出已审核的」条件。分层的价值立刻体现：你只需要改 crud/news.py 里那一个 where，路由层、schema 层、模型层统统不用动，也不会牵连到收藏、历史等其它业务。反之如果 SQL 散落在路由函数里，你就得满项目翻找。

这就是「关注点分离」——把变化的原因收敛到一处。

3目录与文件总览

项目一共 19 个 Python 源文件（不含 .venv 和 __pycache__），分布在 7 个包 + 1 个入口文件里。

文件路径角色作用
main.py入口 创建 FastAPI() 实例 → 注册全局异常处理器 → 挂 CORS 中间件 → include_router 把 4 个路由模块拼进来。整个程序从这里启动。
test_main.http测试脚本 JetBrains IDE 的 HTTP 请求文件，点一下就能发请求测接口，不用开 Postman。
config/db_conf.py基础设施 组装数据库三件套：async_engine（连接池引擎）、AsyncSessionLocal（会话工厂）、get_db()（FastAPI 依赖，管事务与连接回收）。
config/cache_conf.py基础设施 创建全局 Redis 异步客户端，并提供三个最底层函数：get_cache / get_json_cache / set_cache。所有缓存读写最终都走这里。
models/news.pyORM 两个类：Category（新闻分类表）和 News（新闻表）。本文件的 Base 还携带了公共字段 created_at / updated_at。
models/users.pyORM 两个类：User（用户表，含昵称/头像/性别/简介/手机号）和 UserToken（令牌表，一人一条，7 天过期）。
models/favorite.pyORM Favorite（收藏表）。靠 (user_id, news_id) 的联合唯一约束保证同一新闻不会被同一用户重复收藏。
models/history.pyORM History（浏览历史表）。记录谁在什么时候看了哪条新闻。
schemas/base.py契约 NewsItemBase：新闻的公共字段模型（id/标题/简介/封面/作者/分类/浏览量/发布时间），并把 category_id、publish_time 通过 alias 输出成 camelCase。收藏列表和历史列表都继承它，避免重复定义。
schemas/users.py契约 6 个模型：UserRequest(注册/登录入参)、UserinfoResponse(可空资料字段)、UserInfoResponse(完整用户信息，不含 password)、UserAuthResponse(token + userInfo)、UserUpdateRequest(全可选改资料)、UserChangePasswordRequest(新旧密码)。
schemas/news.py契约 RelatedNewsResponse（相关推荐的精简字段：id/标题/图/浏览量）与 NewsDetailResponse（继承 NewsItemBase，加 content 和 relatedNews）。
schemas/favorite.py契约 FavoriteRequest(入参 newsId)、FavoriteCheckResponse(isFavorite)、FavoriteNewsResponse(新闻字段+收藏字段)、FavoriteListResponse(列表+total+hasmore)。
schemas/history.py契约 HistoryAddRequest、HistoryNewsItemResponse(新闻字段+浏览时间+历史id)、HistoryListResponse。结构与收藏那套高度对称。
crud/users.py数据访问 7 个函数：按名查用户、建用户（含 bcrypt 加密）、签发/刷新 token、登录校验、按 token 查用户、更新资料、改密码。
crud/news.py数据访问 新闻相关查询的无缓存版本：分类、列表、计数、详情、浏览量 +1、同类推荐。
crud/news_cache.py数据访问 同样是新闻查询，但每个函数都加了 Redis 缓存（先读缓存 → 未命中查库 → 回写缓存）。目前路由实际调用的是这一版。
crud/favorite.py数据访问 收藏四件事：判断是否已收藏、加收藏、取消收藏、分页取收藏列表（News 与 Favorite join 查询）、清空。
crud/history.py数据访问 历史四件事：记录一次浏览（已有则刷新时间）、分页取列表、删除单条、清空。
cache/news_cache.py缓存 缓存策略层。负责拼 key（如 news_list:1:1:10）、设定过期时间（分类 2 小时 / 列表 30 分钟 / 详情 5 分钟 / 推荐 10 分钟），再转调 config.cache_conf。
routers/users.py路由 5 个接口，前缀 /api/users：注册、登录、取当前用户信息、改资料、改密码。
routers/news.py路由 3 个接口，前缀 /api/news：分类列表、新闻列表（分页）、新闻详情（含浏览量+1 和相关推荐）。含一个私有工具 _news_to_dict() 做 ORM → camelCase 字典转换。
routers/favorite.py路由 5 个接口，前缀 /api/favorite：检查收藏状态、加收藏、取消收藏、收藏列表、清空收藏。
routers/history.py路由 4 个接口，前缀 /api/history：记一次浏览、历史列表、删单条、清空。
utils/security.py工具 bcrypt 密码加密 get_hash_password() 与校验 verify_password()。仅被 crud/users.py 调用。
utils/auth.py工具 核心认证依赖 get_current_user()：从请求头拿 Authorization → 去掉 Bearer → 按 token 查用户 → 有效则注入，无效抛 401。所有需要登录的接口都靠这一行 Depends。
utils/response.py工具 success_response(message, data)：把业务数据包成 {code:200, message, data} 的 JSONResponse，并用 jsonable_encoder 处理 ORM/Pydantic 对象。
utils/exception.py工具 4 个异常处理函数：HTTPException（业务异常）、IntegrityError（唯一键/外键冲突）、SQLAlchemyError（数据库错误）、Exception（兜底）。全部输出统一的 {code, message, data}。
utils/exception_handlers.py工具 register_exception_handlers(app)：把上面 4 个 handler 注册到 app 上。被 main.py 调用。注意注册顺序是具体在前、抽象在后。

顺手一提

把 pageSize 的 le=100 和 newPassword 的 min_length=6 这类约束写在 Query() / Field() 里，是 FastAPI 最省事的安全手段——校验不过自动返回 422，业务代码里一行判断都不用写。

5一次请求的完整旅程

看懂分层最好的方式，是跟着一个真实请求走一遍。下面挑 4 条最有代表性的链路。

5.1 用户注册 — 最完整的一条链路

1
前端发请求 POST /api/users/register，body 是 {"username":"zhang","password":"123456"}。
2
CORS 中间件放行 main.py 里挂的 CORSMiddleware 先判断这个来源能不能访问后端，通过才继续往下。
3
路由匹配 + 入参校验 routers/users.py → register()。FastAPI 用 UserRequest（schemas/users.py）把请求体解析成对象，缺字段或类型不对直接 422，函数体根本不会执行。
4
注入数据库会话 db: AsyncSession = Depends(get_db) 触发 config/db_conf.py 的 get_db()，从连接池领一个 session 出来交给路由函数。请求结束时它会自动 commit / rollback / close。
5
查重 users.get_user_by_username(db, ...) → crud/users.py 拼出 SELECT * FROM user WHERE username = ? 交给 MySQL。查到就抛 400「用户已存在」。
6
加密 + 建用户 create_user() 先调 utils/security.py 的 get_hash_password() 把密码变成 bcrypt 哈希，再 db.add() + commit() 写进 user 表，refresh() 拿回数据库生成的自增 id。
7
签发 token create_token() 用 uuid4() 生成随机串，过期时间 = 现在 + 7 天，写入 user_token 表（已有记录则刷新，保证一人一条）。
8
组装响应 UserAuthResponse(token=..., userInfo=UserInfoResponse.model_validate(user)) —— 注意这里用的是 UserInfoResponse 而不是 User，所以 password 字段天然不会泄露出去。
9
统一格式返回 success_response(message="注册成功", data=...)（utils/response.py）包成 {"code":200,"message":"注册成功","data":{"token":"...","userInfo":{...}}}，前端只需判断 code === 200。

5.2 取新闻列表 — 带缓存的读链路

关键差异是：先问 Redis，Redis 没有才去问 MySQL。这条链路涉及 routers → crud/news_cache → cache/news_cache → config/cache_conf → Redis 共 5 个文件。

# routers/news.py
news_list = await news_cache.get_news_list(db, category_id, offset, page_size)
total     = await news.get_news_count(db, category_id)
has_more  = (offset + len(news_list)) < total
return {"code": 200, "message": "获取新闻列表成功",
        "data": {"list": [_news_to_dict(n) for n in news_list], "total": total, "hasmore": has_more}}

crud/news_cache.py 里做的三件事：

  1. 把 offset 换算成 page（因为缓存 key 用页码更好读）
  2. 调 get_cache_news_list() 读缓存。命中就把存进去的 dict 用 _dict_to_news() 还原成 News 对象返回
  3. 未命中 → 查库 → jsonable_encoder() 转成可 JSON 化的结构 → set_cache_news_list() 回写，过期 1800 秒
这里有个容易踩的坑

缓存里存的是 JSON，原本的 datetime 会变成字符串。所以 _dict_to_news() 必须做一步 datetime.fromisoformat() 反向转换。否则路由层调用 n.publish_time.isoformat() 时，字符串没有这个方法是会直接报 AttributeError 的。

结论：凡是要从缓存还原成对象，就必须处理时间字段的反序列化。

5.3 收藏一条新闻 — 需要登录的写链路

1
前端带 token 请求 POST /api/favorite/add，header 里带 Authorization: Bearer <token>，body 是 {"newsId": 1}。
2
认证依赖先跑 Depends(get_current_user) → utils/auth.py：取出 header 值 → replace("Bearer ", "") 得到纯 token → 调 crud/users.py 的 get_user_by_token() 查 user_token 表并判断是否过期 → 有效则把 User 对象注入到 user 参数。无效则 401，路由函数体不会执行。
3
写库 crud/favorite.py 的 add_news_favorite(db, user.id, body.news_id) → db.add(Favorite(...)) + commit()。
4
统一返回 success_response(message="添加收藏成功", data=result)。
安全上的一个关键点

user_id 来自 token 解析结果，从不从前端传参里取。如果前端能自己传 userId，那任何人都能给别人的账号加收藏。这是「越权」类漏洞最常见的成因。

6逐层逐文件详解

6.1 main.py — 组装车间

它自己几乎不含业务逻辑，只做四件事，顺序很重要：

app = FastAPI()                                  # ① 创建应用实例
register_exception_handlers(app)                 # ② 注册全局异常处理
app.add_middleware(CORSMiddleware, ...)          # ③ 挂跨域中间件
app.include_router(news.router)                  # ④ 挂载 4 个路由模块
app.include_router(users.router)
app.include_router(favorite.router)
app.include_router(history.router)

运行方式：uvicorn main:app --reload。其中 main 是文件名（main.py），app 是文件里的变量名，--reload 表示改代码自动重启（仅开发用）。

启动后打开 http://127.0.0.1:8000/docs 就能看到 FastAPI 自动生成的交互式接口文档，17 个接口全在里面，可以直接点着测。

6.2 config/db_conf.py — 数据库三件套

对象是什么 / 为什么存在
ASYNC_DATABASE_URL连接串，形如 mysql+aiomysql://用户:密码@主机:端口/库名。+aiomysql 就是指定异步驱动。用 os.getenv 优先读环境变量，是为了不把密码写死在源码里。
async_engine引擎，负责管理连接池。pool_size=10 是常驻连接数，max_overflow=20 是高峰时允许临时多开的连接数。有连接池就不用每次请求都重新握手，这是性能的关键。
AsyncSessionLocal会话工厂。引擎管连接，会话管一次工作单元。注意 expire_on_commit=False——默认 True 时，commit 后对象所有属性会失效，下次访问属性会再查一次库（在异步下会直接报错），所以这里必须关掉。
get_db()FastAPI 依赖。用生成器 + yield 把「创建会话」和「收尾」串在一起：正常结束 → commit()；出异常 → rollback() 并重新抛出；无论如何 → close() 把连接还回池子。
 
async def get_db():
    async with AsyncSessionLocal() as session:   # 进：领一个会话
        try:
            yield session                        # 把会话交给路由，暂停在这里等它跑完
            await session.commit()               # 路由正常结束 → 提交事务
        except Exception:
            await session.rollback()             # 出错 → 撤销本次所有未提交修改
            raise                                # 继续抛，交给全局异常处理器
        finally:
            await session.close()                # 无论如何 → 归还连接
为什么 yield 这么重要

它让「事务边界」和「HTTP 请求边界」自动对齐：一个请求就是一个事务。路由函数里即使忘了写 commit，get_db 也会兜底提交；中途任何一步抛异常，前面所有写操作会被整齐地回滚掉，不会留下写一半的脏数据。

6.3 config/cache_conf.py — Redis 底座

创建了一个全局的 redis_client（整个项目共用一个，不要重复创建，否则会撑爆连接数）。对外只暴露三个函数：

函数作用
get_cache(key)取原始字符串，取不到返回 None
get_json_cache(key)取出来顺便 json.loads() 还原成 dict/list
set_cache(key, value, expire)写缓存。value 是 dict/list 时自动 json.dumps；用 setex 一次完成「写入 + 设置过期时间」

三个函数都用 try / except 把异常吞掉只打印日志——这是有意为之：缓存只是加速手段，Redis 挂了业务应该降级去查数据库，而不是让整个接口 500。decode_responses=True 则让读出来直接是字符串，不用每次手动 decode()。

6.4 models/ — 用 Python 类画表

四个文件共定义了 5 张表。写法称为「声明式（Declarative）」：继承 Base → 用 __tablename__ 指定表名 → 用 Mapped[类型] = mapped_column(列类型, 约束...) 声明每个字段。

关于 Base 抽象基类

class Base(DeclarativeBase) 加 __abstract__ = True 表示「我自己不是一张表，只是给子类当模板」。如果漏了这行，SQLAlchemy 会试图把 Base 本身也注册成一张表，启动时直接报错。

这里有一个结构性问题

四个 models 文件各自定义了一遍 Base（见第 9 节 P1-6）。这意味着项目里存在 4 套互不相干的 metadata。而且 models/news.py 的 Base 里塞了 created_at / updated_at 两个公共字段，另外三个文件的 Base 是空的——所以 Category 会「顺带」多出两列，而 Favorite 不会。这种不一致会让建表脚本很难统一，建议抽到独立的 models/base.py。

6.5 schemas/ — 接口的数据契约

Pydantic 模型干两件事：校验进来的数据、规范出去的数据。这里最关键的一个设计是：schemas 和 models 是两套完全独立的类。

models/users.py

User · 数据库的脸

描述数据库表结构，包含 password 字段。它只在内网（和数据库之间）流转，不出现在响应里。

schemas/users.py

UserInfoResponse · 接口的脸

描述返回给前端的结构，从设计上就没有 password 字段。所以即使代码写错也无法泄露密码。

这就是「默认安全」的思路——不是靠记得手写 del user.password，而是靠结构本身让错误不可能发生。

camelCase 别名机制

数据库字段是下划线风格（category_id），前端习惯小驼峰（categoryId）。Pydantic 的 Field(alias=...) 负责这两套命名的自动翻译：

category_id: int = Field(alias="categoryId")     # 输出 JSON 时自动变成 categoryId

model_config = ConfigDict(
    from_attributes=True,    # 允许 model_validate(ORM对象) 直接从对象属性读值
    populate_by_name=True    # 同时也允许用字段名 category_id 构造，两边都能用
)

这几个开关的分工要记清：

  • from_attributes=True —— 没有它，UserInfoResponse.model_validate(user) 会失败，因为它不知道怎么从一个 ORM 对象里取值
  • populate_by_name=True —— 没有它，就只能用别名（categoryId）构造，不能用字段名（category_id）。项目里两处代码各用一种写法，所以必须开

继承与复用

schemas/base.py 的 NewsItemBase 是个典型的「抽公共字段」手法：

NewsItemBase (id/title/description/image/author/categoryId/views/publishTime)
    │
    ├── NewsDetailResponse      + content + relatedNews
    ├── FavoriteNewsResponse    + favoriteId + favoriteTime
    └── HistoryNewsItemResponse + historyId + viewTime

好处是新闻的字段只定义一次，三处接口的字段名永远一致；坏处是改基类会同时影响三处——这正是 schemas/base.py 单独成文件的意义：提醒你这里动一下，三处都会变。

6.6 crud/ — 只和数据库打交道

crud/users.py 的 7 个函数

函数做什么 / 关键细节
get_user_by_username用 scalar_one_or_none() 取值——查不到返回 None 而不是抛异常，这是和 scalar_one() 的关键区别
create_user先 get_hash_password() 加密 → db.add() 登记 → commit() 落库 → refresh() 拿回自增 id

6.7 cache/news_cache.py — 缓存策略

这一层的价值在「决定缓存多久、key 怎么拼」。同样的数据，变化越快缓存越短：

缓存对象key 格式过期时间理由
新闻分类news:category7200 秒（2 小时）分类几乎不变
新闻列表news_list:{分类}:{页}:{每页}1800 秒（30 分钟）会随发布、浏览量变化
新闻详情news:detail:{id}300 秒（5 分钟）单条内容可能被编辑
相关推荐news:related:{id}:{条数}600 秒（10 分钟）推荐结果实时性要求低

缓存 key 的命名约定是 模块:对象:参数，好处是运维时在 Redis 里 KEYS news* 一眼就能看出是什么。

最容易犯的错：读写 key 不一致

set_cache_news_list() 和 get_cache_news_list() 里都有同一行「category_id if category_id is not None else "all"」的规范化逻辑，必须保持完全一致。只要读写两边的 key 拼接差一个字符（比如一边是 None 一边是 all），缓存就永远命中不了，而且不会报错——接口照样返回正确数据，只是每次都查库，性能问题非常隐蔽。

6.8 routers/ — 对外的大门

每个 @router.xxx 装饰的函数就是一个接口。路由层的固定套路是：

@router.post("/add")                                      # ① 声明路径和请求体类型

几处值得单独注意的技巧：

Query 的 alias：给前端 camelCase 的参数名

page_size: int = Query(10, alias="pageSize", le=100)       # le=100 限制每页最多 100 条

响应格式也不统一

routers/news.py 是手写字典 {"code": 200, "message": ..., "data": ...}，其它三个路由用的是 success_response()。输出结果一样，但维护成本不同。

6.9 utils/ — 横切工具

security.py —— 密码为什么不能明文存

数据库一旦泄露，明文密码等于把用户所有账号（他们在别的网站可能用同一个密码）一起交出去。所以存的是 bcrypt 哈希，它的关键特性是不可逆：只能「算出来 → 比对」，不能「从哈希反推明文」。而且每次加密会掺入随机「盐」，同一个密码每次哈希结果都不同，防止「撞库比对」。

环境里有个版本坑（代码注释里也写了）

passlib 1.7.4 与 bcrypt >= 4.1 不兼容，会导致加密直接抛错。必须锁定 bcrypt == 4.0.1。这类「依赖版本不兼容」是 Python 项目最常见的翻车点，值得记住。

auth.py —— 一行 Depends 完成认证

async def get_current_user(authorization: str = Header(..., alias="Authorization"),
                           db: AsyncSession = Depends(get_db)):
    token = authorization.replace("Bearer ", "")     # "Bearer abc" → "abc"
    user = await users.get_user_by_token(db, token)
    if not user:
        raise HTTPException(status_code=401, detail="无效的令牌或已经过期的令牌")
    return user

这是 FastAPI 依赖注入最漂亮的用法：业务路由只要写 user: User = Depends(get_current_user)，就同时获得了「必须登录」和「拿到当前用户」两件事，一行搞定，且不可能忘记校验。

response.py —— 统一响应

def success_response(message="success", data=None):
    content = {"code": 200, "message": message, "data": data}
    return JSONResponse(content=jsonable_encoder(content))

jsonable_encoder 负责把混在 data 里的 Pydantic 对象、ORM 对象、datetime 递归转成能序列化的普通类型，避免手写 json.dumps 时报「Object is not JSON serializable」。

exception.py + exception_handlers.py —— 全局兜底

没有它的时候，任何 raise HTTPException 都会返回 FastAPI 默认的 {"detail": "..."}，和正常响应的 {code, message, data} 结构完全不同，前端要写两套解析逻辑。

加了之后，四种异常全部统一成 {code, message, data}：

处理器HTTP 状态码处理场景
http_exception_handler原样透传业务主动抛的异常，如「用户已存在」（400）、「密码错误」（401）
integrity_error_handler400唯一键冲突、外键失败。会把 Duplicate entry 翻译成「用户名已存在」
sqlalchemy_error_handler500数据库层面的其它错误
general_exception_handler500所有漏网之鱼
注册顺序为什么重要

utils/exception_handlers.py 里的注释写得很清楚：子类在前，父类在后；具体在前，抽象在后。因为 IntegrityError 是 SQLAlchemyError 的子类，如果把 SQLAlchemyError 注册在前面，IntegrityError 就会被父类的处理器截胡，「用户名已存在」这种精准提示就永远出不来。

7数据库表关系

关系读法：

  • user → user_token：一个用户一条令牌记录（业务上刻意限制成 1:1，登录会刷新同一个 token，而不是新增）
  • user → favorite / history：一个用户可以有多条收藏、多条历史
  • news_category → news：一个分类下有多条新闻
  • news → favorite / history：一条新闻可以被多个用户收藏、被多个用户浏览

注意本项目没有使用 ORM 的 relationship() 建立对象级关联，全部靠外键列 + 手写 join 查询。这在学习阶段是好事——你能清楚看到每条 SQL 到底怎么拼出来的。

8四个核心运行机制

8.1 依赖注入与数据库会话生命周期

这是整个项目最值得吃透的机制。流程是：

请求进来
  → FastAPI 发现路由参数上有 Depends(get_db)
  → 调用 get_db()，执行到 yield，把 session 交出去
  → 路由函数开始跑（用这个 session 查库）
  → 路由返回结果
  → 回到 get_db() 的 yield 之后 → commit() → close()
  → 响应发给前端

注意 Depends 是可以嵌套的：get_current_user 自己又 Depends(get_db)，而路由也 Depends(get_db)。FastAPI 在一次请求内会缓存同一个依赖的结果，所以两边拿到的是同一个 session，不会重复创建连接。

8.2 Token 认证链路

注册/登录成功 → uuid4() 生成 token → 存 user_token 表（7 天后过期）
        ↓
前端保存 token → 之后每个请求带 Authorization: Bearer <token>
        ↓
get_current_user() → 去掉 Bearer → 按 token 查表 → 判断 expires_at
        ↓
有效 → 注入 User 对象　｜　无效/过期 → 401

这套方案的特点：有状态（token 存在数据库里，所以服务端可以随时作废它，但每次请求都要查一次库）。生产环境更常见的做法是 JWT（无状态，不查库，但无法主动作废）或「随机串 + 存哈希」。学习阶段这套完全够用。

8.3 旁路缓存（Cache-Aside）

项目采用的缓存模式叫 Cache-Aside，是业界最主流的一种：

读：先查缓存 → 命中就返回 → 未命中则查库 → 回写缓存
写：改数据库 → （理想还要删掉相关缓存）

这里有个必须知道的事实：本项目的写操作没有做缓存失效。也就是说，新闻浏览量 +1 之后，详情缓存里的 views 还是旧值，最长要等 300 秒才更新。

这是 bug 还是设计？

属于「可以接受但要知道」的设计取舍。新闻浏览量、推荐结果这类数据，短暂的不一致对用户体验没有影响，换来的是数据库压力大幅下降。

但如果换成「用户余额」「库存」这类数据，这种延迟就是灾难。判断标准是：这份数据允许多久不一致？超出这个时间用户会明显感知到错误吗？

8.4 统一响应与全局异常

把「成功」和「失败」两条路径的输出都收敛到同一个结构：

成功：success_response(message, data)  →  {"code": 200, "message": "...", "data": {...}}
失败：exception_handler(...)           →  {"code": 4xx/5xx, "message": "...", "data": null}

这样前端只需要一套拦截器：code === 200 取 data，否则把 message 弹出来提示用户。接口约定的稳定性，比接口本身的实现质量更能减少前后端扯皮。

P0-1删除历史接口的参数语义错误（真实 bug）

文件：routers/history.py + crud/history.py

# routers/history.py 第 45-49 行
@router.delete("/delete/{history_id}")
async def delete_history(history_id: int, ...):
    result = await history.delete_history(db, user.id, history_id)   # ← 把 history_id 传成了第三个参数

# crud/history.py 第 43-46 行 —— 第三个参数的形参名叫 news_id
async def delete_history(db, user_id: int, news_id: int):
    query = delete(History).where(History.news_id == news_id, History.user_id == user_id)

后果：URL 里传的是「历史记录 ID」，SQL 却按「新闻 ID」去删。结果是 DELETE FROM history WHERE news_id = {history_id}——要么删不到任何东西（返回 404），要么删错别人那一条新闻的历史记录。这是外键 ID 和业务 ID 混淆的典型案例，一定要修。

修法：把 crud 的函数改成按 History.id 过滤，并加上 user_id 双重条件（防止越权删别人的）：

async def delete_history(db: AsyncSession, user_id: int, history_id: int):
    stmt = delete(History).where(History.id == history_id, History.user_id == user_id)
    result = await db.execute(stmt)
    await db.commit()
    return result.rowcount > 0

P0-2重复收藏会返回「用户名已存在」

文件：utils/exception.py + crud/favorite.py

favorite 表的 (user_id, news_id) 上方挂了联合唯一约束。用户重复点击收藏时，MySQL 抛 Duplicate entry，而全局处理器的判断逻辑是：

if "username_UNIQUE" in error_msg or "Duplicate entry" in error_msg:
    detail = "用户名已存在"      # ← 收藏重复也被塞进这个分支

后果：用户收藏失败，提示语却是「用户名已存在」，非常困惑。而且 unique=True 自动生成的约束名未必叫 username_UNIQUE，这个判断本身就不牢靠。

修法：加收藏前先判断是否已收藏（`crud/favorite.py` 里已经有 `is_news_favorite()` 可以直接用），业务层面拦掉；异常处理器按表名分支而不是按约束名猜。

P0-3数据库密码明文硬编码 + SQL 日志全量打印

文件：config/db_conf.py

ASYNC_DATABASE_URL = os.getenv("DATABASE_URL",
    "mysql+aiomysql://root:真实密码@localhost:3306/news_app?charset=utf8mb4")   # ← 兜底值就是生产密码
async_engine = create_async_engine(..., echo=True)   # ← 每条 SQL 都打到控制台，含参数

用 os.getenv 的思路是对的，但「默认值兜底」等于把密码写死在仓库里——一旦代码推到 Git 就等于泄露。echo=True 在开发时很方便，但生产会拖慢性能，并且把 SQL 参数（可能含手机号）写进日志。

修法：去掉默认值，让环境变量缺失时直接启动失败；echo 跟随一个 DEBUG 环境变量。同时把已经写进 Git 的密码轮换掉（改密码，不只是删代码）。

P0-4CORS 全开放 + 允许携带凭证

文件：main.py

allow_origins=["*"], allow_credentials=True

开发阶段图方便可以理解，但要清楚它意味着任何网站都能带着用户的凭证访问你的接口。上线前必须换成前端的具体域名白名单。同时建议把 token 认证方式确认一下是放 header 而不是 Cookie——放 header 时 CSRF 风险天然更低。

P1 · 结构性问题

P1-1models 里定义了 4 个 Base，且携带字段不一致

四个模型文件各自 class Base(DeclarativeBase)，导致 4 套独立的 metadata。更麻烦的是 models/news.py 的 Base 带 created_at/updated_at，其它三个是空的——于是 Category 会凭空多出两列，Favorite 没有。后续想写统一的建表/迁移脚本时会很难办。

修法：新建 models/base.py 定义一个 Base（把公共字段决定清楚），其余四个文件 from models.base import Base。

P1-2crud/news.py 与 crud/news_cache.py 大量重复

两个文件几乎一模一样，routers/news.py 同时 import 两个，导致「取新闻列表」有两条实现路径。更隐蔽的问题是两者的返回结构不一致：

  • crud/news.py 的 get_related_news() 返回含 content 的全字段字典（且是列表推导式里现拼的）
  • crud/news_cache.py 的 get_related_news() 返回 RelatedNewsResponse 只有 4 个字段

目前路由用的是后者，所以前者里除了 get_news_count 和 increase_news_views，其余函数实际上已经是死代码。

修法：保留 news_cache.py，把其中缓存逻辑做成可开关的（比如给函数加一个 use_cache: bool = True 参数），删掉重复文件。或者在 crud/news.py 里直接调用带缓存版，避免同一个功能两套实现。

P1-3响应格式两种风格并存

routers/news.py 手写 {"code": 200, ...}，其它三个路由用 success_response()；序列化上 news 用手写 _news_to_dict()，favorite/history 交给 Pydantic 模型。输出一致但维护成本高——将来要给所有响应加一个 timestamp 字段，就得改两个地方，还容易漏。

修法：统一改用 success_response() + Pydantic 响应模型（其实 schemas/news.py 里已经有 NewsDetailResponse 了，只是路由没用上）。

P1-4索引命名有误导性

Index("username_UNIQUE", "username")   # 名字里有 UNIQUE，但它只是普通索引！

真正的唯一性来自列上的 unique=True，而不是这个索引名。同理 token_UNIQUE 也是。这会让后来看代码的人误以为索引提供了唯一保证。另外这属于重复约束（unique=True 已经自动建了唯一索引，再建一个普通索引是浪费）。

修法：删掉这两个多余的 Index，或者改名成 idx_user_username 这类诚实的名字。

P1-5缺少 Authorization 头返回 422 而不是 401

文件：utils/auth.py

authorization: str = Header(..., alias="Authorization")   # ... = 必填

必填意味着「没带这个头」会被 FastAPI 当成参数校验失败，返回 422 加一堆 schema 细节。而「token 无效」返回 401。前端拦截器通常只处理 401（跳登录页），422 会被当成别的错误。

修法：改成可选（Header(None, alias="Authorization")），在函数体里判断为空时主动抛 401，语义就统一了。

P1-6DEBUG_MODE 硬编码为 True

文件：utils/exception.py。开启时异常响应会带上 traceback 完整堆栈、SQL 错误原文、请求路径——对攻击者是很有价值的信息。教学阶段方便，上线前必须改成读环境变量。

P2 · 细节改进

级别位置问题与建议
P2routers/news.py
get_categories		返回的分类字段是 sort_order（snake_case），其它接口统一 camelCase，前端要写两套取值逻辑。建议统一成 sortOrder。
P2crud/favorite.py
get_favorite_list		select(func.count()).where(...) 依赖 SQLAlchemy 从 where 子句反推 FROM，会产生「笛卡尔积」告警。建议显式写 func.count(Favorite.id)。
P2routers/favorite.py用 news.__dict__ 构造响应，会把 SQLAlchemy 内部的 _sa_instance_state 一起带进去（Pydantic 会忽略，但写法脆弱）。建议显式列出字段，或让 Pydantic 用 from_attributes 直接从对象取。
P2schemas/favorite.py
schemas/history.py		has_more 的别名是 "hasmore"（小写 m），不符合小驼峰风格。虽然前后端已经约定如此，但如果要改，趁项目还小最省事。
P2models/ 各文件整个项目所有包目录都没有 __init__.py（靠 Python 3.3+ 的命名空间包机制运行）。目前能跑，但打包、做类型检查、换工具链时容易出问题。建议补上空的 __init__.py。
P2crud/users.pycreate_user / create_token 内部 commit()，而 get_db() 收尾时还会再 commit 一次。功能上无害，但事务边界应该只有一处。建议统一交给 get_db()，crud 只负责 add()。
P2crud/history.py
delete_history		唯一一个没写 commit() 的函数（靠 get_db 兜底）。同文件其它函数都写了，风格不一致，容易让人误以为它会自动提交。
P2main.py没有 Base.metadata.create_all()，表必须手工在 MySQL 里建好才能跑。建议补一个建表入口脚本并写进 README，否则换台机器部署就卡住。
P2config/cache_conf.pyRedis 连接参数（host/port/db）全部硬编码在源码里，且不支持密码。建议同样是「环境变量 + 无默认值」。
P2utils/response.pysuccess_response 无条件返回 HTTP 200。这是常见约定（用业务码判断成败），但要确保前端拦截器不依赖 HTTP 状态码，否则会遇到「明明出错却走成功分支」的问题。
P2crud/users.py
create_token		token 是 uuid4 明文入库、固定 7 天、无刷新机制、无签名。学习够用；生产建议用 JWT 或「随机串 + 存哈希」，并支持滑动续期。
P2schemas/users.pyUserProfile 类的命名大小写不一致（UserinfoResponse 里的 info 是小写 i）。小问题，但既然要改不如一次改整齐。
一个问题值得单独说：缓存 key 的读写一致性

cache/news_cache.py 里 set_cache_news_list 和 get_cache_news_list 各自维护了一份 key 拼接逻辑。任何一边改了（比如把 "all" 改成 "ALL"）都会导致缓存静默失效——接口不报错、数据也对，只是每次都查库。这类 bug 极难发现。

建议：把 key 拼接抽成一个私有函数 _news_list_key(category_id, page, size)，读写都调它。这样「一致性」就由代码结构保证，而不是靠人记得。
